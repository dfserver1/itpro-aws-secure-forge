Lección 1 · Modelo de Responsabilidad Compartida ⭐ base de Security

🏠 Analogía cero: Imagina que alquilas una caja fuerte en un banco. El banco (AWS) asegura el edificio, cámaras, la caja en sí y que no se incendie. Tú aseguras la combinación, qué guardas y a quién le das copia. Si dejas la caja abierta y roban tus papeles, no es culpa del banco.

Qué es: El modelo que divide quién asegura qué. Security OF the cloud = AWS (físico, red, hipervisor). Security IN the cloud = TÚ (tus datos, usuarios IAM, cifrado, firewall Security Group).

Para qué sirve: Saberlo te evita el error #1 del examen y del trabajo: creer que AWS “te protege de todo”. No — si haces un bucket público, AWS no te salva.

Ejemplo real: Subes dni.pdf a S3 sin Block Public Access. Google lo indexa y se filtra. En la auditoría te preguntan “¿falló AWS?” — respondes: “No, fallé yo (IN), faltó bucket policy + SCP/RCP + Macie”.

Cómo se ve en consola: S3 → Permissions → Block all public access: ON (tú decides). EC2 → tu Windows/Linux → tú parchas.

Error común: Pensar que “AWS cifra mi S3 solo”. No — tú activas SSE-S3 o SSE-KMS.

Conecta con: Lección 2 (Regiones/AZ: dónde vive físicamente ese S3) y Lección 3 (Red: quién puede llegar a él).

Lección 2 · Regiones y Zonas de Disponibilidad

🏠 Analogía: Región = ciudad donde está el banco (Lima, São Paulo, Virginia). AZ = 3 sucursales separadas por km en esa ciudad, con luz y red distintas pero conectadas por fibra privada.

Qué es: Región sa-east-1 / us-east-1 es ubicación física de data centers. AZ 1a/1b/1c son data centers aislados dentro de la región.

Para qué sirve: Elegir dónde viven tus datos (ley GDPR, latencia Perú) y sobrevivir si una AZ se cae. Si pones todo en 1a y se cae, te caes.

Ejemplo real: App de trámites de una municipalidad: eliges us-east-1 para piloto barato con 6 AZ, despliegas EC2 en 1a y 1b + ALB. Si 1a cae, 1b responde.

Cómo se ve: Arriba derecha en consola el selector de región. Factura cambia según región (São Paulo 15-25% más cara que Virginia).

Error común: Creer que AWS replica solo entre regiones. No — tú decides replicar (S3 CRR, RDS Global).

Lección 3 · Redes: IP, CIDR, DNS, puertos

🏠 Analogía: IP = dirección de casa. CIDR = cuántas casas hay en tu calle: /16 = barrio grande (65k casas = VPC), /24 = cuadra (256 casas = subred), /32 = 1 casa. Puerto = puerta de la casa: 443 (HTTPS, blindada), 22 (SSH, llave maestra).

Qué es: VPC 10.0.0.0/16 es tu barrio privado. Subred pública tiene Internet Gateway (calle con salida), privada no. DNS (Route53) traduce banco.pe → IP.

Para qué sirve: Sin entender CIDR no puedes crear VPC en Fase 2 y sin puertos no entiendes SG. 0.0.0.0/0 en SG 22 = dejas la puerta maestra abierta al mundo.

Ejemplo real: Web en EC2: SG inbound 443 desde 0.0.0.0/0 (todo el mundo a tu web vale), pero 22 solo desde tu IP/32 o mejor sin 22 y usa SSM Session Manager.

Cómo se ve: VPC → CIDR 10.0.0.0/16 → Subnets 10.0.1.0/24 (a) y 10.0.2.0/24 (b) → Route Table 0.0.0.0/0 → IGW solo en pública. Prueba en cidr.xyz.

Error común: Poner 0.0.0.0/0 en 22/3389 “para probar” y olvidar — es la causa #1 de ransomware.

Conecta con: Lección 4 (terminal: cómo entrar sin abrir 22) y Fase 1 C1 (EC2 vive dentro de esta red).

F1 · Lección 3 · Bases de datos: RDS, Aurora, DynamoDB

F1 · Lección 4 · Redes: ALB, Route 53, CloudFront

🏠 Analogía: Route53 = guía telefónica (banco.pe → IP). ALB = recepcionista que reparte fila entre cajeros (EC2). CloudFront = fotocopias en cada sucursal (Edge) para no ir hasta la central.

Qué es: ALB reparte HTTP por path (ej. /api → grupo 1, /img → grupo 2) y hace health checks. Route53 traduce nombres, hace failover entre regiones si health falla. CloudFront copia tu S3/ALB en 600 Edges, baja latencia y costo.

Para qué sirve: Web rápida, alta disponibilidad y barata: S3 (web) → CloudFront (Edge) → Route53 (banco.pe).

Error común: Poner CloudFront sin Origin Access Control y dejar S3 público, o no poner health check y el failover nunca ocurre.

S1 · VPC profundo: subredes, route tables, NAT, endpoints

🏠 Analogía: VPC = barrio privado con calles (Route Tables). Subred pública = calle con portón a la calle (IGW). Privada = calle sin salida. NAT = portero que deja salir a comprar pero no entrar.

Qué es: VPC 10.0.0.0/16 abarca 3 AZ. Subred 10.0.1.0/24 (a-pública) y 10.0.11.0/24 (a-privada). NAT Gateway en pública da internet a privadas (para parches). Endpoint Gateway para S3/Dynamo evita internet. NACL stateless (subred), SG stateful (instancia).

Para qué sirve: Aislar DB en privada sin exponerla, pero que pueda descargar parches; y que S3 no salga por internet (más seguro/barato).

Ejemplo real: App 3 capas: ALB en públicas, App/EC2 en privadas con NAT, RDS en privadas aún más aisladas, S3 vía endpoint.

Cómo se ve: VPC → Subnets → Route Tables: pública 0.0.0.0/0 → IGW, privada 0.0.0.0/0 → NAT. VPC → Endpoints → Create Gateway para s3.

Error común: Poner NAT en privada (no funciona) o olvidar habilitar DNS hostnames y endpoint falla.

S4 · Desacoplamiento: SQS, SNS, Kinesis, EventBridge

🏠 Analogía: SQS = buzón donde dejas carta y el otro la recoge cuando puede. SNS = megáfono que grita a muchos buzones a la vez. Kinesis = cinta transportadora que puedes rebobinar. EventBridge = centralita que enruta eventos.

S5 · Alta disponibilidad & DR: Route53, CloudFront, backup

🏠 Analogía: HA = tener 2 sucursales abiertas; DR = tener plan si se incendia una. RPO = cuántos papeles pierdes, RTO = cuánto tardas en reabrir.

Qué es: Pilot Light = DB replica encendida, resto apagado (barato). Warm Standby = todo encendido pero pequeño. Multi-Site = todo activo 100%. Route53 failover con health checks cambia DNS si región cae. AWS Backup centraliza snapshots.

Para qué sirve: Si us-east-1 cae, tu web sigue en us-east-2 sin perder más de 1h de datos (RPO) y en 15 min arriba (RTO).

Error común: Creer que backup = DR (backup es copia, DR es plan probado) o no probar failover nunca.

SCS D5 · Data Protection (KMS, S3, EBS, RDS encryption)

🏠 Analogía: Envelope = metes tu carta en sobre chico (data key) y ese sobre en caja fuerte (CMK). Bucket Key = reutilizas el mismo sobre para todas las cartas del cajón.

Qué es: S3 Bucket Key baja costo KMS 99%. RDS encryption solo al crear (si no, snapshot cifrado + restore). EBS default encryption cifra todo nuevo. ACM renueva cert solo. Secrets vs Parameter = Secrets rota y cobra.

Para qué sirve: Cifrar sin arruinarte en llamadas KMS y no olvidar renovar cert.

Ejemplo real: S3 con SSE-KMS + Bucket Key ON: 1M objetos → 1 llamada KMS vs 1M sin Bucket Key. RDS no cifrado → creas snapshot → Copy with encryption → restores.

Cómo se ve: S3 → Properties → Default encryption → SSE-KMS → Bucket Key Enable. KMS → Automatic rotation ON.

Error común: Crear RDS sin cifrar y creer que luego “Enable encryption” existe (no, hay que migrar).
